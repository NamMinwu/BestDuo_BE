## 1. 결정 요약

`bottom_duo_matchup_agg` 의 카운터 조회 쿼리(`findCountersByLowestWinRate`) 정렬 키를 **단순 승률** 에서 **베이지안 보정 승률** 로 변경한다.

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 정렬 키 | `wins / games` ASC (단순 승률) | `(wins + 20) / (games + 40)` ASC (베이지안 스무딩) |
| 2차 정렬 | `games DESC` | `games DESC` (유지) |
| 최소 게임 수 필터 | 없음 | 없음 (스무딩이 노이즈를 정렬에서 자연스럽게 밀어냄) |
| Prior | — | `α = β = 20` (prior 승률 0.5, "20판 정도 누적 시 실제 승률 절반 반영") |
| 응답 DTO | `BottomDuoCounterResponse` (winRate 필드는 실제 승률) | **불변** — 정렬에만 보정값 사용, `winRate`는 그대로 실제 승률 노출 |

`findCountersByLowestWinRate` 메서드 시그니처와 응답 DTO 필드는 **일체 변경하지 않는다**.

---

## 2. 문제 정의

### 2-1. 관찰된 현상

매치 상세 화면의 카운터 추천에서, **표본이 매우 작은 매치업이 카운터 상위에 노출**되는 사례가 발생.
구체적으로 1게임 0승(승률 0%) 매치업이 200게임 30% 승률(진짜 카운터)보다 상위에 표시되어 추천의 신뢰성이 떨어짐.

### 2-2. 데이터 분포

`bottom_duo_matchup_agg` 의 매치업당 게임 수:
- 최소: **1 게임**
- 분포 폭이 매우 큼 (1 ~ 수백 판)

매치업은 `(myAdc, mySup, oppAdc, oppSup)` 4-튜플로 분할되기 때문에 듀오 통계 대비 매치업당 표본 수가 훨씬 작다.
1~5게임짜리 매치업이 상당수 존재하며, 단순 승률(0%, 100% 같은 극단값)이 정렬 최상위로 올라오기 매우 쉬운 구조.

### 2-3. 기존 식의 구조적 결함

`BottomDuoMatchupAggregateJpaRepository.java:175-193` 의 기존 쿼리:

```sql
order by
  (case when games = 0 then 0 else (wins::double precision / games) end) asc,
  games desc
limit :limit
```

| 결함 | 효과 |
|---|---|
| ① 1차 정렬이 **단순 승률** | 1판 0승(승률 0%) > 200판 30% (승률 30%) — 표본 무관하게 극단값이 우선 |
| ② 2차 정렬 `games DESC` 는 **동률 시에만 작동** | 승률이 다르면 1차 정렬이 모든 걸 결정. 2차 정렬은 사실상 무의미한 케이스가 대부분 |
| ③ 최소 게임 수 필터 없음 | 1게임짜리 매치업도 그대로 후보에 포함 |

→ "내가 가장 적게 이긴 상대" 라는 의도는 맞지만, **표본 신뢰성을 전혀 반영하지 않음**.

## 3. 결정 — 베이지안 스무딩 (옵션 B 단독)

### 3-1. 보정 공식

```sql
order by
  (wins::double precision + 20) / (games + 40) asc,
  games desc
limit :limit
```

- Prior 승률 = 0.5 (`α / (α + β) = 20 / 40`)
- 표본 수가 작으면 0.5에 가까운 값으로 수렴 → 카운터 상위 진입 불가
- 표본 수가 커지면 prior 영향이 자연 감소 → 실제 승률에 수렴

### 3-2. α = β = 20 선정 근거

- `α = β = 20` → 약 20판 누적 시 prior와 실제 표본이 절반씩 영향. 일반적인 매치업 표본 분포에 맞춤.
- 더 작은 값(10)은 5~10판짜리도 빠르게 상위 진입 가능 → 노이즈 잔존.
- 더 큰 값(30)은 신규 패치/신규 챔피언이 반영되기까지 오래 걸림.
- `(α, β)` 가 동일하므로 prior가 정확히 0.5로 중립적이며, 카운터(낮은 승률) 쪽이든 친화 매치업(높은 승률) 쪽이든 동일하게 보정.

### 3-3. 메서드 시그니처/응답 DTO 불변 원칙

| 항목 | 정책 |
|---|---|
| `findCountersByLowestWinRate(...)` 시그니처 | 불변 (호출처 `BottomDuoMatchupFinder` 영향 없음) |
| `BottomDuoMatchupAggregate` 엔티티 | 불변 |
| `BottomDuoCounterResponse.Item.winRate` | **실제 승률 그대로 노출** — UI는 사용자가 이해 가능한 단순 승률을 봄 |
| 보정 승률 | **DB 정렬 식 내부에서만 계산** — Java/응답으로 전파하지 않음 |

이유: 사용자(end-user)가 보는 "승률" 은 직관적이어야 함. 보정값을 UI에 노출하면 "왜 1판 0승짜리가 48.8%로 표시되지?" 라는 혼란 발생. 정렬 순서만 신뢰성을 갖추면 충분.

## 4. 검증 시나리오 — 변경 전/후 대조

가정: 동일 티어/패치, 동일 `myAdc/mySup` 에 대한 상대 듀오 후보 5개.

| 케이스 | games | wins | 단순 승률 | 보정 승률 (신, α=β=20) |
|---|---|---|---|---|
| **A** 1판 0승 (노이즈) | 1 | 0 | **0.0%** | **0.488** (= 20/41) |
| **B** 3판 1승 (노이즈) | 3 | 1 | 33.3% | 0.488 (= 21/43) |
| **C** 50판 15승 (약한 카운터) | 50 | 15 | 30.0% | **0.389** (= 35/90) |
| **D** 200판 70승 (강한 카운터) | 200 | 70 | 35.0% | **0.375** (= 90/240) |
| **E** 100판 40승 (보통) | 100 | 40 | 40.0% | 0.429 (= 60/140) |

### 정렬 결과 비교 (오름차순)

| 시스템 | 1위 | 2위 | 3위 | 4위 | 5위 |
|---|---|---|---|---|---|
| **변경 전** (단순 승률) | A (0%) | B (33%) | C (30%) | D (35%) | E (40%) |
| **변경 후** (보정 승률) | **D (0.375)** | **C (0.389)** | E (0.429) | A (0.488) | B (0.488) |

**핵심 변화:**
1. **D(200판 35%, 진짜 강한 카운터)가 1위로 올라옴** — 표본과 승률 모두 신뢰할 만한 매치업이 보상받음.
2. **C(50판 30%)가 2위** — 적당한 표본의 진짜 약한 매치업.
3. **A(1판 0승, 노이즈)는 4위로 추락** — 의도한 결과.
4. B도 동률 근처로 밀려남.

> 사용자가 보는 응답에서 `winRate` 필드는 여전히 0.0% / 33.3% / 30.0% / 35.0% / 40.0% 로 표시됨. 정렬 순서만 신뢰성 있게 바뀜.

## 5. 트레이드오프 — 명시적 비교

### 5-1. 거부된 대안

#### A안: 최소 게임 수 필터 (`HAVING games >= N`)

```sql
where ... and games >= :minGames
```

- **장점:** 변경 최소(WHERE 절 한 줄). 직관적("최소 N판 이상만").
- **거부 이유:**
  1. **Cliff 현상** — N-1판과 N판 사이에 단절. N=20이면 19판 매치업은 영영 안 보임.
  2. **결과 개수 부족 가능** — counterSize=10인데 인기 없는 매치업 조합에선 N판 이상이 10개 안 나올 수 있음.
  3. **임계값 N 튜닝 부담** — 데이터 분포 따라 자주 조정 필요.
  4. **카운터 후보 영구 배제** — 진짜 좋은 카운터인데 표본이 N 미만이면 영원히 발견 못함.

#### C안: Wilson lower bound

- **장점:** 통계적으로 가장 엄밀.
- **거부 이유:**
  1. SQL 식이 매우 길어짐(제곱근, 정규분포 quantile). 가독성/유지보수성 저하.
  2. 카운터(낮은 승률)에서는 의미상 *upper bound* 를 써야 정확 — 직관 반전.
  3. Java 후처리로 처리하면 페이지네이션/limit 처리가 복잡해짐.
  4. B 대비 추가 가치 작음 — B로도 노이즈 제거 효과는 충분.

#### A+B 조합 (필터 + 스무딩)

- **거부 이유:**
  1. 두 파라미터(N, α/β) 모두 튜닝 필요 — 복잡도 증가.
  2. A의 cliff 현상이 그대로 잔존.
  3. `min games = 1` 데이터에선 B 단독으로도 충분 — A는 과잉.

### 5-2. 채택안의 트레이드오프

#### 비용 1 — Prior 강도가 다소 보수적

`α = β = 20` 은 20판 정도 누적되어야 실제 승률이 절반 반영됨. 매우 강한 카운터(예: 5판 5승 = 100% 카운터)도 보정 후 25/45 ≈ 0.556 → 카운터 상위 진입 못함.

- **반대 의견:** "5판 5승은 통계적으로 의미 있는 신호인데 묻히는 건 과한 거 아닌가?"
- **현재 답:** 사용자 문제 정의가 "신뢰성 부족" 이므로 보수적 방향으로 기울이는 게 맞음. 표본 작은 강한 신호는 시간이 지나면 자연스럽게 표본 누적되어 상위로 올라옴.

#### 비용 2 — 새 매치업/패치 초반 반영 지연

신규 패치 직후엔 모든 매치업이 1~10판 수준이라 보정 승률이 prior(0.5) 근처에 몰림 → 카운터 변별력 일시 저하.

- **완화책:** 패치 적재 후 시간이 지나면 자연 해소. 별도 대응 불필요.
- **모니터링 지표:** 신규 패치 적재 후 첫 24시간 동안 카운터 응답의 표본 분포.

#### 비용 3 — 보정값을 UI에 노출하지 않는 데서 오는 정보 손실

UI는 단순 승률만 보여주므로 사용자가 "왜 1판 0승이 카운터 1위가 아닌가?" 를 직접 확인하기 어려움.

- **완화책:** `games` 필드는 이미 응답에 포함됨(`BottomDuoCounterResponse.Item.games`). UI에서 "N게임 기준" 같은 부가 표시를 활용하면 사용자가 신뢰성을 가늠 가능.
- **Future Work:** 필요 시 `smoothedWinRate` 를 별도 필드로 추가하되, 별도 결정으로 미룸 (YAGNI).

### 5-3. Prior 강도 `α = β = 20` vs `10` vs `30` 비교

| 케이스 | 단순 승률 | α=β=10 | α=β=20 (채택) | α=β=30 |
|---|---|---|---|---|
| 1판 0승 | 0.0% | 0.476 | 0.488 | 0.492 |
| 5판 5승 | 100% | 0.600 | 0.556 | 0.538 |
| 50판 15승 (30%) | 30.0% | 0.357 | 0.389 | 0.409 |
| 200판 70승 (35%) | 35.0% | 0.364 | 0.375 | 0.385 |

- α=β=10: 노이즈는 잘 잡지만 5~10판 강한 신호가 빠르게 반영됨(0.6 ≈ 카운터 상위 진입 가능).
- **α=β=20 (채택):** 적당히 보수적. 50판 정도 모이면 실제 승률 차이가 정렬에 명확히 드러남.
- α=β=30: 더 보수적이지만 200판 매치업도 prior 영향이 남아 있음 → 과한 보수.

### 6-2. 데이터 마이그레이션

`bottom_duo_matchup_agg` 테이블 스키마/데이터는 **일체 건드리지 않음**. 정렬 식만 변경되므로 배포 즉시 효과 발생.

### 6-3. API 응답 영향

- 응답 DTO 필드/타입 변경 없음. 프론트엔드 영향 없음.
- 카운터 응답의 **순서**만 바뀜. 1~5판짜리 노이즈 매치업이 상위에서 사라지고, 표본 충분한 매치업이 상위 차지.
- `winRate` 필드는 여전히 실제 승률(`wins/games`) 그대로.

## 7. Future Work (미반영, 향후 결정)

1. **`smoothedWinRate` 필드 추가 여부** — 사용자 피드백 후 결정. 정렬에만 쓰는 현재 정책으로 충분한지 관찰.
2. **Prior 강도 자동 튜닝** — 데이터 누적 후 α/β 그리드 서치 가능.
3. **친화 매치업(`findTopWinRateDesc`)에도 동일 스무딩 적용 검토** — 카운터와 정반대 방향이지만 동일한 노이즈 문제 존재 가능. 별도 ADR 로 다룰 예정.
4. **티어별 prior 차등화** — 챌린저/마스터처럼 표본이 적은 티어에 더 강한 prior 적용 검토 가능.
